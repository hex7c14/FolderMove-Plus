# 国际化（i18n）开发说明

FolderMove-Plus 的界面支持多语言，**默认跟随系统语言**，也可以在侧边栏底部手动切换。

当前内置语言：

| 语言 | code | 状态 |
| --- | --- | --- |
| 简体中文 | `zh-CN` | 源语言，文案的第一手来源 |
| English | `en-US` | 已翻译 |
| 繁體中文 | `zh-TW` | 已翻译 |
| 日本語 | `ja-JP` | 已翻译 |

---

## 1. 技术选型

| 组件 | 作用 |
| --- | --- |
| [i18next](https://www.i18next.com/) `^26` | 翻译核心：插值、复数、回退 |
| [react-i18next](https://react.i18next.com/) `^17` | React 绑定：`useTranslation()`，语言切换自动重渲染 |
| `Intl`（浏览器内置） | 日期、数字、字节单位的本地化格式，以及按语言排序 |

语言包**直接打进 bundle**（`import xx from "./locales/xx.json"`），不做按需加载：
Tauri 是本地应用，多几十 KB 无所谓；好处是 `initI18n()` 可以同步完成，
首帧就是正确语言，不会出现「先英文后中文」的闪烁。

> ⚠️ **资源结构必须是两层的**：i18next 的寻址方式是 `resources[语言][命名空间]`，
> 默认命名空间是 `translation`，所以 `resources.ts` 里必须写成
> `{ "zh-CN": { translation: zhCN } }`。少写这层 `translation` 的话，
> 所有 `t("nav.apps")` 都查不到，界面会直接显示 key 本身——
> 而这个错误 `tsc` 看不出来（`initI18n()` 里有启动自检会 `console.error` 提醒）。

## 2. 目录结构

```
src/i18n/
├─ index.ts          initI18n() / changeLocale() / onLocaleChange()
├─ types.ts          Locale 联合类型、语言元数据、系统语言归一化
├─ resources.ts      语言包登记处（新增语言只改这里 + types.ts）
├─ keys.ts           K：文案 key 常量表（动态 key 必须走它）
├─ codes.ts          与 Rust 约定的消息码类型（错误 / 原因 / 进度 / 阶段）
├─ useLocale.ts      useLocale()：当前语言 + 用户偏好 + 切换
├─ i18next.d.ts      i18next 类型增强（写错 key 直接编译报错）
└─ locales/
   ├─ zh-CN.json     ← 源语言，新增文案先写这里
   ├─ en-US.json
   ├─ zh-TW.json
   └─ ja-JP.json

src/lib/
├─ errors.ts         后端「码 + 参数」→ 当前语言的文案
├─ useFormatters.ts  随语言变化的字节 / 日期 / 数字 / 排序
└─ useWindowTitle.ts 窗口标题跟随语言（运行时切换用）

src-tauri/src/locale.rs   系统语言探测 + 窗口初始标题（原生侧，见 §7.1）

scripts/check-i18n.mjs  语言包一致性检查（pnpm i18n:check）
```

## 3. 日常用法

### 3.1 组件里取文案

```tsx
import { K, useTranslation } from "../i18n";

function Foo() {
  const { t } = useTranslation();
  return <span>{t(K.list.move)}</span>;      // "移动" / "Move"
}
```

带插值：

```tsx
t(K.toast.moved, { name: app.display_name, size: bytes(rec.size_bytes) })
// 已移动「微信」，释放 1.24 GB
// Moved “WeChat”, freed 1.24 GB
```

### 3.2 为什么要有 `K`

`src/i18n/i18next.d.ts` 把 key 类型收紧到「源语言里存在的 key」，
所以 `t("list.mov")` 这种拼写错误会在 `tsc` 阶段就报错。

但**运行时拼出来的 key** 无法静态校验，比如「风险等级 → 文案」：

```tsx
// ✗ 类型上是 string，类型检查帮不上忙
t(`list.risk.${level}`)

// ✓ 用 K 保证字面量类型，拼错 key 同样编译报错
t(K.list.risk[level])
```

所以规则是：**key 需要映射表或动态拼接时，一律走 `K`。**

### 3.2.1 ⚠️ 一个很容易踩的坑：别把命名空间对象当字符串用

`K` 是**嵌套对象**，只有叶子才是字符串。写成模板字符串会把对象插值掉：

```tsx
// ✗ K.units 是 { B: "units.B", GB: "units.GB", ... } 这个对象
//   模板字符串 → "[object Object].GB" → key 查不到
//   i18next 查不到 key 会把 key 原样返回，界面就显示 "78.2 [object Object].GB"
t(`${K.units}.${unit}`)

// ✓ 逐项取值，拿到的才是字符串 "units.GB"
t(K.units.GB)
t(K.units[unit])          // unit: "B" | "KB" | ... | "PB"
```

判断标准很简单：**`K` 下面还能再点一层就是个对象，不能参与字符串拼接。**
`K.list.risk`、`K.units`、`K.reason`、`K.progress.phase`、`K.progressMessage`
都是这种命名空间对象，要么 `K.list.risk[level]`，要么 `K.progressMessage.copyingTo`。

（`pnpm build` 的类型检查**抓不到这个错误**：`t()` 对未知 key 会退化成一个宽松重载，
`as never` 又能绕过它。所以这类改动之后最好在界面上扫一眼，或按下面第 10 节的清单自测。）

### 3.3 新增一条文案

1. 在 `src/i18n/locales/zh-CN.json` 里写好中文（放对语义分组，如 `list` / `dialog` / `error`）
2. 如果它需要被动态引用，在 `src/i18n/keys.ts` 的 `K` 里加一行
3. 补 `en-US.json` / `zh-TW.json` / `ja-JP.json`
4. `pnpm i18n:check` 确认没有漏 key，`pnpm build` 确认类型没问题

### 3.4 新增一门语言

1. 复制 `src/i18n/locales/zh-CN.json` 为新文件 `<code>.json` 并翻译
2. `src/i18n/types.ts`：在 `Locale` 联合类型和 `LOCALES` 数组里加上这个 code
3. `src/i18n/resources.ts`：import 并登记（**记得包一层 `{ translation: xx }`**）
4. 如果这门语言的复数规则不是「只有一种」，在 `scripts/check-i18n.mjs` 的
   `SINGLE_PLURAL` / `NON_CJK` 里补一下

语言下拉框、`<html lang>`、窗口标题、日期数字格式都会自动跟上。

## 4. 后端消息码契约（重要）

Rust 后端**不返回拼好的句子**，只返回「消息码 + 参数」：

```json
{ "code": "insufficientSpace", "params": { "needed": 1073741824, "available": 536870912 } }
```

前端用 code 去语言包取 `error.insufficientSpace`，所以**切换语言时，
历史错误信息、正在进行的进度提示也会跟着翻译**。

### 4.1 消息码的三处同步点

改一个码要同时改这三个地方，缺一处就会界面显示成 `error.xxx` 或直接回退成原始英文：

| 位置 | 内容 |
| --- | --- |
| `src-tauri/src/error.rs` | `AppError::code()` / `params()` 里返回的码与参数 |
| `src/i18n/codes.ts` | `ErrorCodeParams` / `ProgressMessageCodeParams` 类型 |
| `src/i18n/locales/*.json` | `error.*` / `reason.*` / `progressMessage.*` 四份文案 |

现有码的分类：

- `error.*` —— 失败信息（`AppError`）
- `reason.*` —— 扫描出来的「风险说明 / 不可移动原因」码（`scan.rs::classify`）
- `progressMessage.*` —— 进度事件里的明细文案（`ProgressPayload.messageCode`）
- `progress.phase.*` —— 进度阶段标题，前端按 `phase` 自己映射

### 4.2 兼容性

`src/lib/errors.ts` 的 `describeError()` 做了三层兜底：

1. `{ code, params }` 结构化错误 → 查语言包
2. 未知的 code → 用 `error.other` 把原始内容显示出来（不会白屏）
3. 纯字符串 / `Error`（旧版后端、系统错误）→ 原样展示

所以前端可以和后端分开升级，不会因为一处不一致就崩。

### 4.3 前端渲染后端文案的正确姿势

**保持原始值，渲染时再翻译**，不要在处理错误时就翻译成字符串存进 state：

```tsx
// ✓ 语言切换后，屏幕上已有的错误提示也会跟着变
const [error, setError] = useState<unknown>(null);
...
{error && <div>{describeError(t, error)}</div>}
```

```tsx
// ✗ 翻译结果被冻结在出错那一刻的语言
setError(String(e));
```

## 5. 格式化与排序

组件里统一用 `useFormatters()`，不要自己拼字符串：

```tsx
const { bytes, dateTime, number, compare } = useFormatters();

bytes(1536)                    // 1.50 KB
dateTime("2025-01-02T03:04Z")  // 2025/01/02 11:04 · 1/2/2025, 11:04 AM · 2025/01/02 11:04
number(12345)                  // 12,345
compare("微信", "QQ")           // 按当前语言排序（中文按拼音）
```

字节单位本身也走语言包（`units.*`），所以哪天要译成「バイト」只需改 JSON。

## 6. 语言偏好

- 存储位置：`localStorage["fm-plus-locale"]`
- 取值：`"system"`（默认，跟随系统）或某个 `Locale`
- 系统语言归一化在 `types.ts::normalizeLocaleTag()`：
  `zh-Hans-CN → zh-CN`、`zh-Hant-TW / zh-HK / zh-MO → zh-TW`、`en-GB → en-US`，
  认不出来则回退到 `zh-CN`
- 切换时会同步更新 `<html lang>`、`<html data-locale>`、`document.title`
  和 Tauri 原生窗口标题

### 7.1 窗口标题为什么要分两处实现

| 时机 | 由谁设置 | 原因 |
| --- | --- | --- |
| 窗口刚创建 | Rust（`src-tauri/src/locale.rs`） | 不依赖 WebView 加载完成，第一眼就是正确语言 |
| 用户切换语言 | 前端（`src/lib/useWindowTitle.ts`） | 运行时只能走 IPC |

两个坑，都踩过：

1. **ACL 权限**：`core:default` 里只有读标题的 `allow-title`，**没有**写标题的
   `set_title`。要在 `src-tauri/capabilities/default.json` 里显式加
   `core:window:allow-set-title`，否则 `getCurrentWindow().setTitle()` 会被拒绝。
2. **别静默吞异常**：一开始这里写的是 `.catch(() => {})`，结果权限问题完全无声，
   窗口标题一直是空的，排查了很久。现在开发模式下会 `console.warn` 出来。

`src-tauri/src/locale.rs` 里的语言码必须和 `src/i18n/locales/*.json` 对齐，
新增语言时两处都要改（那个文件里有测试守着，漏了会 `cargo test` 失败）。

## 7. 刻意**不**翻译的东西

| 内容 | 原因 |
| --- | --- |
| 软件名 / 发布者 / 安装路径 | 来自注册表和文件系统，是数据不是文案 |
| 默认落盘目录名 `FolderMove-Plus` | 真实目录名，翻译后会让用户在磁盘上找不到东西；也与 `get_default_target` 保持一致 |
| `robocopy`、`NTFS Junction`、`FSCTL_SET_REPARSE_POINT` | 技术专有名词，译了反而看不懂 |
| Rust 内部的 `Display` 实现 | 只进日志，界面上一律走消息码 |

- 插值变量名（`{{name}}` / `{{size}}` / `{{count}}`）**不能改**，只调整它们在句子里的位置。

## 9. 复数与数量

i18next 按 `count` 自动选复数形式：

| 语言 | 需要的后缀 |
| --- | --- |
| `zh-CN` / `zh-TW` / `ja-JP` | 只有 `_other` |
| `en-US` | `_one` + `_other` |

```json
// en-US.json
"count_one":   "{{count}} app",
"count_other": "{{count}} apps"

// zh-CN.json
"count_other": "共 {{count}} 个软件"
```

调用时传 `count` 即可：`t(K.list.count, { count: number(filtered.length) })`。
`pnpm i18n:check` 会检查带 `_other` 的条目在英文包里是否漏了 `_one`。

## 10. 自检清单

改完多语言相关代码后跑一遍：

```bash
pnpm i18n:check    # 语言包 key 是否对齐、是否有漏翻
pnpm build         # tsc 会校验所有 t() 的 key 是否正确
cd src-tauri && cargo test --lib   # 含语言探测/错误序列化的单元测试
```

人工确认（`pnpm tauri dev`）：

- [ ] 侧边栏底部切换语言，界面立刻变化，无需重启
- [ ] 重启后语言记忆还在；选「跟随系统」会跟着系统走
- [ ] 进度浮层、错误提示在切换语言后是当前语言
- [ ] 窗口标题、任务栏标题是当前语言
- [ ] 英文/日文下界面没有被截断或换行错乱（长文案的地方尤其注意）
- [ ] **界面上搜不到 `[object Object]` 和 `xxx.yyy` 这种英文小写点号串**
      —— 前者是命名空间对象被拼进了 key（见 3.2.1），后者是 key 拼错了。
      i18next 查不到 key 时会原样显示 key，不会报错，所以只能靠肉眼扫。
